## 0. Що це і навіщо

Шість анотованих 4K-кадрів реакторного токамака з плазмою, придатних для
відкриття хакатону, слайдів і статей. Плазма не вигадана: її топологію взято
з **реального розряду DIII-D 203702, кадр 75 (t = 1760 мс)**, а всі числа, які
з'являються на зображенні, походять з одного файлу `manifest.json`, який
згенерував конвеєр. Зображення й документ не можуть розійтися.

Проєкт закриває наявну прогалину. У `Our try/02-field-map/F-poincare-and-topology.md`, §7:

> **Для лекції на відкритті:** фотографія проколів з W7-X поруч із контурами ψ
> від EFIT. Одне — розв'язана обернена задача, де перетин зайвий; інше —
> виміряний перетин поля, яке ніхто не вміє обернути. **Хакатон живе в цьому
> проміжку.**

## 1. Виправлення до початкового технічного завдання

Ці пункти сформульовано відкрито, а не застосовано мовчки.

**1.1. Blender не має власного імпортера STEP/IGES** — у жодній версії 4.x чи
5.x. Розділ CAD замінено на процедурну побудову. Для цього проєкту це до того ж
краще: геометрію керує реальний профіль камери й реальна таблиця з 19 котушок
із файлу розряду, тож її можна перебудувати з іншого розряду.

**1.2. В осесиметрії перетин Пуанкаре — це точно лінії рівня ψ.** Це власний
установлений результат проєкту. Острови не можна «дістати» з реконструкції
EFIT; їх треба **свідомо й підписано** внести.

**1.3. Вакуумний перетин систематично ПЕРЕОЦІНЮЄ стохастичність** — плазма
екранує резонансні компоненти. Згідно з §5 `F-poincare-and-topology.md`, це
застереження друкується **на кадрі**, а не ховається у виносці.

**1.4. DIII-D не має ні берилію, ні вольфрамового дивертора, ні кріостата** —
це мідна теплá машина з графітовими плитками. Набір матеріалів із брифу — це
ITER. Розв'язано «реакторним композитом» (§1.6).

**1.5. ITER у перегляді базової лінії 2024 року перейшов з берилію на вольфрам**
для першої стінки. Обидва матеріали реалізовано; берилієва панель підписана як
конструкція до 2024 року.

**1.6. Масштабування.** Рівновага — справжній DIII-D (R₀ = 1,678 м, a ≈ 0,67 м),
а машина — реакторного класу. Застосовано **рівномірне перетворення подібності**
s = 3,0 → R₀ = 5,03 м, a ≈ 2,01 м. Оскільки масштаб рівномірний, аспектне
відношення не змінюється (2,5), а отже **q(ψ) і вся топологія силових ліній
інваріантні**. Тому кадр може чесно нести топологію реального розряду в
реакторному масштабі. Це **не** заявка «це ITER» (аспектне відношення 3,1).

**1.7. У EEVEE об'ємна емісія не освітлює поверхні.** Плазма — головне джерело
світла у сцені, тож у реальному часі внутрішній об'єм камери був би чорний.
Додано кільце допоміжних ламп (`plasma_proxy_lights`), яке вимикається для
Cycles, де все працює фізично правильно.

**1.8. `scipy.interpolate.interp2d` видалено** і він підіймає виняток на
встановленому SciPy 1.18.1 (у `Tokamak-GS-solver` він трапляється в 6 місцях).
Наш код його не використовує.

## 2. Архітектура конвеєра

Ключове обмеження: **Blender 5.2 несе Python 3.13 і numpy 2.3.4, але не несе
scipy**. Тому вся важка математика виконується поза Blender, а Blender лише
читає масиви.

```
   parquet розряду (CC BY 4.0, НЕ в репозиторії)
            │
            ▼
   ┌─────────────────────────────┐   venv: numpy, scipy, pyarrow, skimage
   │  src/tokviz/  (фізика)      │
   │  equilibrium → perturbation │
   │  → fieldline → islands      │
   │  → surfaces → export        │
   └─────────────┬───────────────┘
                 ▼
        data/bake01/*.npz + manifest.json     ← єдине джерело правди для чисел
                 │
                 ▼
   ┌─────────────────────────────┐   Blender 5.2: bpy + numpy (без scipy)
   │  src/blender/tokblend/      │
   │  bl → materials → machine   │
   │  → plasma → cutaway         │
   │  → cameras → render → comp  │
   └─────────────┬───────────────┘
                 ▼
        tokamak.blend  →  render/*.png
                 │
                 ▼
        src/annotate.py  (matplotlib + PIL, знову у venv)
                 ▼
        render/*_annotated.png
```

Запуск від початку до кінця:

```bash
# 1. фізика
python src/run_bake.py --out data/bake01

# 2. сцена + рендер
blender --background --python src/blender/build_scene.py -- \
        --bake data/bake01 --out tokamak.blend --render both

# 3. анотації
python src/annotate.py --bake data/bake01 --render-dir render
```

## 4. Фаза P1 — Підготовка даних

**Модуль:** `src/tokviz/equilibrium.py`

1. `load_shot()` читає рядок parquet: `efit_psirz (166, 65, 65)`, `efit_times`,
   `efit_grid_R/Z`, `efit_q95`, `efit_lcfs_r/z (166, 90)`, таблицю 19 котушок
   (`coil_R/Z/width/height/angle1/angle2`).
2. `select_frame()` бере кадр із скінченним ψ у вікні плато, у якого q95
   найближчий до 3,7 — низький q95 заганяє резонанси q = 1, 2, 3 всередину
   плазми, де острови великі й читабельні. → **кадр 75, t = 1760 мс, q95 = 3,6995**.
3. Сітка приходить як float32, тож «рівномірна» вісь має ~1,4·10⁻⁷ м розкиду.
   `_regularize()` прив'язує її до точного `linspace`, якщо відхилення менше
   0,1 % комірки, і відхиляє справді нерівномірну сітку.
4. `find_axis()` — грубий argmax по `axis_sign·ψ` у внутрішній частині сітки,
   далі Nelder–Mead по сплайну.
5. `set_boundary_from_contour()` бере ψ_bdy як медіану ψ уздовж **власного**
   `efit_lcfs_r/z` набору даних — нормування збігається з EFIT, а не
   перевиводиться.

**QA-контроль (виміряно):**

| Перевірка | Результат |
|---|---|
| вісь проти `efit_r_axis`/`efit_z_axis` | **ΔR = 0,0002 мм, ΔZ = 0,0001 мм** (комірка 26,6 × 50,0 мм) |
| розкид ψ уздовж LCFS | 8,2·10⁻⁵ = **0,022 %** діапазону потоку |

## 5. Фаза P2 — Математика плазми

**Модулі:** `equilibrium.py`, `perturbation.py`, `fieldline.py`, `islands.py`
Повні викладки — у `docs/PHYSICS.md`.

### 5.1. Поле

```
B_R = −(1/R) ∂ψ/∂Z      B_Z = +(1/R) ∂ψ/∂R      B_φ = F(ψ)/R
```

на `RectBivariateSpline` від ψ (C²-похідні; **не** `interp2d`).

### 5.2. Калібрування F — набір даних не містить `fpol`

q лінійне за F, тому одне ділення:

```
F = 2π·q95_EFIT / ∮ dl/(R|∇ψ|)      (контур ψ_N = 0,95)
```

**Результат:** F = 3,23341 Т·м → **B_φ(вісь) = 1,927 Т**. Реальне тороїдальне
поле DIII-D — 1,9–2,1 Т. Ми відновили справжнє поле машини з q95 і геометрії,
не подавши жодної інформації про B₀. Це незалежна перевірка всього ланцюга.

### 5.3. Прямокутний кут θ* і чому це критично

Збурення `cos(mθ − nφ)` резонує точно на `q = m/n` лише якщо θ — **прямокутний
кут силової лінії**:

```
θ*(ℓ) = 2π · [∫₀^ℓ dl/(R|∇ψ|)] / [∮ dl/(R|∇ψ|)]
```

Табулюємо **різницю** Δ = θ* − θ_geo, а не сам θ*: обидва кути набирають рівно
2π за оберт, тож Δ однозначна й 2π-періодична, мала й гладка. Сам θ* має розріз
на 2π, який знищив би похідні сплайна.

> **Виміряний урок.** Перша реалізація растеризувала `cos(mθ*)` на сітку 65×65.
> Розклад назад по поверхні показав **2,4 % паразитної гармоніки m = 1**, і в
> перетині з'явився **фальшивий ланцюг островів на q = 1**, хоча збурення
> містило лише m = 2 і m = 3. Ширина острова йде як √амплітуди, тож навіть
> мале спектральне забруднення видно. Аналітичне обчислення знизило паразитну
> m = 1 до **0,4 %**, і фальшивий острів зник.

### 5.4. Збурення

```
ψ_total(R,Z,φ) = ψ(R,Z) + Σ_k A_k g_k(ψ_N) cos(m_k θ* − n_k φ + α_k)
B = ∇×(ψ_total ∇φ)     ← дивергенція нульова ТОЧНО, бо це ротор
```

Обвідні: `vacuum` (`ψ_N^(m/2)`, росте до краю як зовнішнє вакуумне поле) та
`resonant` (гаусіана на резонансній поверхні). Обидві з C¹-загасанням поза
сепаратрисою.

Ширина острова з маятникової сепаратриси: `W = 4√(ε q/|dq/dψ_N|)` — залежність
від m скорочується. Канонічна пара — (θ\*, ψ_t) з гамільтоніаном ψ; до
2026-09-29 тут стояло `4√(ε q²/|dq/dψ|)`, що завищує W у √q раз (див.
`docs/PHYSICS.md` §4 і `docs/CHANGES-2026-09-29-island-width.md`).

### 5.5. Трасування

```
dR/dφ = −(R/F) ∂ψ_total/∂Z        dZ/dφ = +(R/F) ∂ψ_total/∂R
```

`solve_ivp`, **DOP853**, `rtol` 1e-9…1e-10. Усі зерна інтегруються одним
пакетним вектором стану; лінія, що вийшла за сітку, «заморожується», щоб не
зривати спільний адаптивний крок.

### 5.6. Контрольні точки якості (виміряно)

| Перевірка | Результат |
|---|---|
| q з контурного інтеграла проти q **з трасування** | збіг **0,001–0,16 %** при ψ_N = 0,3…0,95 |
| дрейф ψ уздовж осесиметричних ліній, 200 обертів | **1·10⁻⁷ … 1,4·10⁻⁶** — лише похибка інтегратора |
| незбурений перетин | відтворює контури ψ (теорема осесиметрії як модульний тест) |
| паразитні гармоніки | ≲ 1,3 % від цільової моди |

Резонансні поверхні кадру 75: **q = 1 на ψ_N = 0,335; q = 2 на 0,752; q = 3 на 0,900**.

При m/n = 2/1 і 3/1, амплітуда 10⁻³:

```
2/1  ψ_N = 0,7520  ε = 7,52e-4  dq/dψ_N = 4,44   W = 0,0736
3/1  ψ_N = 0,9001  ε = 8,54e-4  dq/dψ_N = 10,70  W = 0,0619
Чириков S = 0,458   (менше 1 — поверхні між ланцюгами виживають)
(до виправлення √q 2026-09-29: W = 0,104 / 0,107, S = 0,714)
```

Перетин показує **2 острови на q = 2 і 3 на q = 3** — ланцюг m/n мусить давати
m островів у полоїдальному розрізі — а поверхні між ними цілі, як і належить
при S < 1.

## 6. Фаза P3 — Процедурна машина

**Модуль:** `src/blender/tokblend/machine.py`. Жодного CAD.

| Деталь | Побудова |
|---|---|
| Вакуумна камера | профіль LCFS, зміщений назовні на 0,10 м, обернений навколо Z |
| PF-котушки (19) | **виміряна таблиця розряду**: `coil_R/Z/width/height/angle1/angle2` |
| TF-котушки (18) | профіль камери, зміщений на 0,32 м, вирізаний по φ + Solidify + Bevel |
| Кріостат | згладжена розширена оболонка машини |
| Дивертор | нижня ділянка профілю камери, витягнута вниз |
| Броньові плитки | окрема оболонка всередині камери, розбита на панелі з зазором |
| Патрубки (12) | циліндри крізь стінку на екваторі |

**Переріз котушки.** Набір даних зберігає котушку як центр, ширину, висоту й два
кути зсуву (конвенція EFIT `AC`/`AC2`): `angle1` нахиляє горизонтальні ребра,
`angle2` — кут вертикальних ребер до осі R, тож 90° — це прямокутник без зсуву.

> **Пастка:** `angle2 == 0` означає «не задано», а **не** «зсув 0°». Більшість
> F-котушок DIII-D мають `angle1 = angle2 = 0` і є звичайними прямокутниками.
> Ділення на `tan(0)` тут дає нескінченний зсув.

**Стек модифікаторів TF-котушки:**

```
Mesh (вирізаний сектор профілю)
  └─ Solidify   thickness = 0.32·s,  offset = 0.0
  └─ Bevel      width = 0.04, segments = 2, limit_method = ANGLE
  └─ Cutaway    (GeometryNodes, §9)
```

**Не заявляйте «Princeton D».** Крива постійного натягу визначається умовою
силової рівноваги, а не параметрами форми. Тут використано **параметризацію
Міллера** (`d_shape`: витягнутість κ, трикутність δ) — вона точна як
означення й стандартна у фізиці токамаків, але це інша крива.

**QA-контроль:** внутрішній профіль камери збігається з маскою оболонки;
немає немноговидої геометрії; сцена тримається в бюджеті для інтерактивного
EEVEE.

## 7. Фаза P4 — Геометрія плазми

**Модуль:** `src/blender/tokblend/plasma.py`

- **Вкладені поверхні потоку** — 14 рівнів ψ_N ∈ [0,12; 0,97], кожна з ψ_N,
  записаним як атрибут вершини (`store_attribute`), який читає шейдер.
- **Об'єм плазми** — оболонка LCFS як обмежувальна сітка для об'ємного шейдера.
- **Силові лінії** — попередньо протрасовані **справжні** лінії як криві з
  `bevel_depth`. Це фізично правильно й дешево; інтегрувати поле всередині
  Geometry Nodes не потрібно.
- **Проколи Пуанкаре** — вершинна сітка + GN-інстансер сфер.

> **Чому вершинна сітка, а не `PointCloud`:** датаблок `bpy.data.pointclouds`
> існує, але заповнюється через `PointCloud.resize(n)`, а **не**
> `points.add()`. Вершинна сітка з GN-інстансером поводиться однаково на 4.2 і
> 5.x та значно легше шейдиться й масштабується.

**Анімація частинок (за потреби).** Частинки їдуть по **попередньо
протрасованих справжніх силових лініях** через `GeometryNodeSampleCurve`
(`mode='FACTOR'`), зсунутих за часом сцени. Варіант із Simulation Zone, що
інтегрує запечене векторне поле, лишається як «живіший» режим. Магнітний зсув
береться прямо з протрасованого q-профілю.

## 8. Фаза P5 — Шейдери

**Модуль:** `src/blender/tokblend/materials.py`. Усе авторовано так, щоб **одне**
дерево вузлів рендерилось в обох рушіях.

### 8.1. Об'ємна плазма

ψ_N осесиметрична, тобто залежить лише від (R, Z). Тому її можна запакувати у
**float-зображення** й семплити точно — жодних аналітичних наближень:

```
TexCoord.Object ─► SeparateXYZ ─┬─► Math(MULTIPLY x·x) ─┐
                                └─► Math(MULTIPLY y·y) ─┴─► Math(ADD) ─► Math(SQRT) = R
                                                                              │
   SeparateXYZ.Z ──────────────────────────────────────────────────┐          │
                                                                   ▼          ▼
                                            MapRange(Z→v)   MapRange(R→u)
                                                       └────► CombineXYZ ────► ImageTexture(psi_n)
                                                                                    │ Color = ψ_N
      ┌─────────────────────────────────────────────────────────────────────────────┤
      ▼                                     ▼                                       ▼
 ColorRamp(DensityProfile)          ColorRamp(EmissionProfile)              MapRange(ψ_N→T)
      │ B_SPLINE, 1→0                       │ 1→0 при 0,92                          │ 11000→1800 K
      ▼                                     ▼                                       ▼
 Math(MULTIPLY) ◄── MapRange(TurbGain) ◄── NoiseTexture(4D, FBM)              Blackbody
      │                                     │                                       │
      ▼                                     ▼                                       ▼
 Math(MULTIPLY ×density) ──► Density   Math(MULTIPLY ×emission) ──► Emission Strength
                                                                     Blackbody.Color ──► Emission Color
                                        ▼
                              PrincipledVolume ──► MaterialOutput.Volume
```

`NoiseTexture` у 4D: вхід `W` — час, тож та сама сітка дає анімовану
турбулентність без зміни дерева. `Musgrave` більше не існує — його типи
(`FBM`, `MULTIFRACTAL`, `RIDGED_MULTIFRACTAL`, `HYBRID_MULTIFRACTAL`,
`HETERO_TERRAIN`) тепер у `noise_type` вузла Noise.

> **Фізична чесність.** Градієнт «гаряче ядро → холодний край» — це те, що
> просить бриф і що читається як «плазма». Справжня **фотографія у видимому
> світлі** — навпаки: ядро надто гаряче, щоб випромінювати у видимому, і
> виглядає темним, а світиться холодний край через лінійчасте випромінювання.
> Не підписуйте такий кадр як фотореалістичний.

### 8.2. Зношений метал (вольфрам, берилій, сталь, мідь)

```
TexCoord.Object ─► Mapping(scale = (70, 2.5, 2.5))  ─► NoiseTexture(FBM) ─┬─► «шліфування»
                 └► Mapping(scale = (24.5, 1.2, 1.2)) ─► Voronoi(DISTANCE_TO_EDGE)
                                                             └► ColorRamp(вузький) ─► Math(×scratch)
                                                                                          │
   «шліфування» ──────────────────────────────────────────────► Math(ADD) ◄───────────────┘
                                                                     │ Height
                     ShaderNodeBevel(radius, ТІЛЬКИ Cycles) ─► Bump.Normal
                                                                     ▼
                                                                   Bump ─► Principled.Normal
   «шліфування» ─► MapRange(rough−0.10 … rough+0.14) ─────────────► Principled.Roughness
   TexCoord.Object ─► SeparateXYZ.Z ─► MapRange ─► Math(×heat) ─► ColorRamp(кольори відпуску)
                                                                  └─► Principled.Base Color
   ShaderNodeTangent(RADIAL, Z) ────────────────────────────────► Principled.Tangent
   Principled: Metallic = 1, Anisotropic = preset, Specular IOR Level = 0.5
```

Кольори відпуску в `ColorRamp`: база → солом'яний (0,30) → коричневий (0,52) →
фіолетовий (0,72) → глибокий синій (1,0). Це справжня послідовність кольорів
мінливості сталі, і вона миттєво читається як «ця деталь працювала гарячою».

Пресети (`METAL_PRESETS`): `tungsten` (aniso 0,65; heat 0,75), `beryllium`
(матовий, heat 0,25), `steel` (полірований 316LN), `copper` (резистивні
котушки в стилі DIII-D).

> **Cycles-only вузли.** `ShaderNodeBevel` і `ShaderNodeAmbientOcclusion`
> створюються в будь-якому рушії, але **EEVEE їх ігнорує**: Bevel пропускає
> нормаль без змін, AO повертає біле. Те саме з `Geometry → Pointiness`. Тому
> знос будується процедурними текстурами, а Bevel лишається підсиленням для
> фінального Cycles.

## 9. Фаза P6 — Розріз, камери, світло

**Модуль:** `src/blender/tokblend/cutaway.py`. Три механізми, усі від **одного**
параметра 0 → 1, тож набір кадрів і майбутня анімація йдуть з однієї оснастки.

### 9.1. Основний: Geometry Nodes (без кришок, швидко, точно)

```
GroupInput.Geometry ──────────────────────────────► DeleteGeometry.Geometry
InputPosition ─► SeparateXYZ ─► Math(ARCTAN2 y,x) = φ
                                    │
GroupInput.Start ─────► Math(SUBTRACT) ─► Math(WRAP 0..2π)
                                                    │
GroupInput.Cut ─┐                                   │
GroupInput.Width┴► Math(MULTIPLY) = ефективний клин  │
                                    └──────────────► Math(LESS_THAN) ─► DeleteGeometry.Selection
                                                          DeleteGeometry(domain=FACE, mode=ALL) ─► GroupOutput
```

### 9.2. Запасний: Boolean із суцільним клином (з кришками)

`GeometryNodeMeshBoolean` / модифікатор `BOOLEAN`, `operation='DIFFERENCE'`.
У 5.x доступний **`solver='MANIFOLD'`**, помітно надійніший за `EXACT` на
згенерованій геометрії.

### 9.3. Реального часу: відсічення в шейдері

`Geometry.Position → VectorMath(DOT_PRODUCT) → Math(LESS_THAN) → MixShader` з
`TransparentBSDF`; матеріал переводиться у `'BLENDED'`. Для лекції, де
переобчислення модифікатора гальмує в'юпорт.

> **Три помилки, знайдені на практиці:**
> 1. **Клин має відкриватися ДО камери.** Камери стоять на азимутах −125°…−140°;
>    клин на −45°…+45° вирізається з протилежного боку й невидимий. Центруйте
>    його на −135°.
> 2. **Об'ємну сітку плазми різати НЕ можна.** Фроксельні об'єми EEVEE
>    потребують замкненої межі; розрізаний об'єм рендериться як плоскі плити.
>    Поверхні потоку різати **треба** — інакше вкладеність не читається взагалі.
> 3. **Кожній камері — власна ціль `TRACK_TO`.** Спільний порожняк виглядає
>    охайно, але переміщення його для останньої камери мовчки перенаводить усі
>    попередні.

### 9.4. Камери

Відстань виводиться з **реального габаритного радіуса сцени**, не з R₀:
`d = margin · radius · 2·lens / sensor`. Кріостат приблизно вдвічі ширший за
R₀, тож кадрування «по R₀» заганяє камеру **всередину машини** — саме це
сталося в першому проході.

### 9.5. Світло

Потужність теж від відстані: `P = irradiance · 4π d²`. Лампи, розставлені за
R₀, опиняються всередині кріостата й повністю вибілюють кадр.

Для EEVEE додається кільце з 8 допоміжних ламп на магнітній осі, **виключене з
Cycles**, щоб не рахувати світло двічі.

## English summary

A production blueprint for a six-image 4K still set of a reactor-class tokamak,
built in Blender 5.2.1 LTS with EEVEE for look-development and Cycles/Metal for
finals, on an Apple M4.

**What makes it defensible.** The plasma is not invented: its topology comes
from DIII-D discharge 203702, frame 75 (t = 1760 ms), and every number printed
on the image is read from the `manifest.json` the pipeline wrote, so the render
and the document cannot drift apart.

**Corrections to the original brief, stated openly.** Blender has no native
STEP/IGES importer in any 4.x or 5.x release, so the CAD chapter is replaced by
a procedural build driven by the measured vessel profile and the real 19-coil
table. In strict axisymmetry a Poincaré section is exactly the level sets of ψ,
so magnetic islands must be introduced deliberately and labelled — and a vacuum
section systematically *overestimates* stochasticity, a caveat printed on the
image rather than buried. DIII-D has no beryllium, no tungsten divertor and no
cryostat; those belong to the reactor-class composite, reached by a **uniform**
similarity scale (s = 3.0) that leaves the aspect ratio, q(ψ) and the entire
field-line topology invariant.

**The physics core.** F(ψ) is absent from the dataset, so it is calibrated
against the dataset's own q95 — one division, since q is linear in F. The
result, B_φ = 1.927 T on axis, matches DIII-D's real 1.9–2.1 T toroidal field,
recovered without supplying any information about B₀. The perturbation is
written on the straight-field-line angle θ*, evaluated analytically rather than
rasterised: rasterising onto the coarse 65×65 grid leaked 2.4% spurious m = 1
and produced a fake island chain at q = 1 from a perturbation containing only
m = 2 and m = 3. Validation: the magnetic axis matches EFIT to 0.0002 mm, the
contour-integral and traced safety factors agree to 0.001–0.16%, ψ drifts by
~10⁻⁷ over 200 toroidal turns, and the section shows exactly 2 islands at q = 2
and 3 at q = 3, as an m/n chain must.

**Blender specifics.** Every node name, socket and enum was verified by
introspecting the actual build; the API reference records the 4.2 → 5.x
differences that break scripts outright — Geometry Nodes modifier inputs moved
from `mod["Socket_2"]` to `mod.properties.inputs`, `Fac` became `Factor`, the
compositor moved to `Scene.compositing_node_group` with `NodeGroupOutput`,
Glare's settings became menu sockets whose `Size` changed from an integer 1–9 to
a 0–1 float, EEVEE lost Bloom at 4.2, and `Musgrave` was folded into the Noise
Texture at 4.1.

**Performance.** With Metal kernels cached, a 480×320 frame with volume renders
in 1.13 s on the M4 GPU, extrapolating to roughly 8 minutes per 4K still at
256 spp — under an hour for the whole set. The first Cycles render of any
session additionally pays a one-off ~100 s Metal kernel compilation, which is
easy to mistake for a performance problem.
